# API 설계 배경

엔드포인트의 **모양**은 Swagger UI 가 보여줍니다 (`/swagger-ui.html`).
이 문서는 거기 담을 수 없는 **"왜 그렇게 되어 있나"** 만 다룹니다.

규약(응답 봉투·오류 코드·페이지네이션)은 [`api-conventions.md`](api-conventions.md),
한 번 정하면 되돌리기 어려운 선택은 [`decisions/`](decisions/) 에 있습니다.

---

## 1. 이벤트 상태

| 값 | 의미 |
| --- | --- |
| `DRAFT` | 임시저장 |
| `PUBLISHED` | 게시중 |
| `ENDED` | 게시종료 (**종단**) |

`DRAFT → PUBLISHED → ENDED` 단방향입니다. `ENDED` 에서 되돌아오지 않습니다 (REQ-EVT-07).

다만 **게시 내리기는 예외**입니다. `PUBLISHED → DRAFT` 로 돌아갑니다 — 잘못 올린 것을 즉시
내리는 경로가 필요하기 때문입니다. 대신 **종료 시각이 지난 이벤트는 내릴 수 없습니다**
(`409 EVENT409-1`). 내리면 `DRAFT` 가 되어 수정 잠금이 풀려서, 끝난 이벤트를 고쳐 다시
게시할 수 있게 되기 때문입니다.

### 자동 종료는 스케줄러가 합니다

기본 1분마다 `status = PUBLISHED` · `deletedAt = null` · `endDate < now` 인 이벤트를 `ENDED` 로
바꿉니다. 시작일·종료일은 그대로 두고 상태와 `updatedAt` 만 바꿉니다.

**그래서 "종료 시각은 지났는데 아직 PUBLISHED" 인 창이 최대 1분 존재합니다.** 이 틈 때문에
여러 곳이 상태만 보지 않고 기간도 같이 봅니다.

- 참여 API 는 스케줄러와 무관하게 기간을 직접 검증합니다
- 알림의 `STARTED` 는 `endDate > now` 를 같이 봅니다 — 이미 끝난 이벤트에 시작 알림을
  보내지 않으려고요
- 공개 상세는 기간 밖이면 `404` 로 답합니다

## 2. `closingSoon` 은 저장 컬럼이 아닙니다

조회할 때마다 계산합니다. 저장하면 시간이 흘러도 값이 안 바뀌어서, 3일 전이 지났는데도
`true` 로 남습니다.

판정 규칙입니다.

```
종료일이 없으면            false
아직 시작 전이면           false
그 외에는  now <= endDate 이고 endDate 가 now + 3일 이내이면 true
```

**시작 전을 빼는 이유** — 기간이 긴 이벤트는 시작도 전에 종료일만 가까워져 "마감임박" 으로
뜰 수 있습니다. 아직 참여도 못 하는 이벤트에 마감임박은 틀린 말입니다.

3일은 기획 확정 전 임시값입니다 (REQ-EVT-15).

> ⚠️ 관리자 쪽 판정은 `Event` 엔티티로 옮겼지만 **공개 쪽(`PublicEventService`)에 같은 계산이
> 남아 있습니다.** 지금은 답이 같지만, 창을 5일로 바꾸면 관리자 화면과 사용자 화면이
> 달라집니다. 통합이 필요합니다.

## 3. 저장 HTML 의 슬롯은 비어 있습니다

이벤트 페이지 HTML 은 **슬롯이 빈 채로** 저장되고, 보여줄 때 채웁니다.

```html
<!-- 저장된 것 -->
<p data-slot="period"></p>

<!-- GET /api/public/events/{id} 가 돌려주는 것 -->
<p data-slot="period">2026.09.22 ~ 10.06</p>
```

**저장할 때 채우면 그 값이 굳습니다.** 이벤트 기간만 고쳐도 화면이 안 바뀝니다.

그래서 `publishedHtml` · `thumbnailHtml` 은 **엔티티에서 직접 꺼내면 안 됩니다.**
`PublicEventService.publishedHtmlOf()` · `ThumbnailHtml.of()` 를 거쳐야 합니다.
직접 꺼내면 슬롯이 빈 HTML 이 그대로 나갑니다.

자세한 배경은 [`decisions/0001-슬롯은-보여줄-때-채운다.md`](decisions/0001-슬롯은-보여줄-때-채운다.md).

## 4. 공개 API 는 "없는 것처럼" 답합니다

공개 기간(`startDate ~ endDate`) 밖이면 **존재 자체를 노출하지 않습니다** (REQ-PUB-02).

| 상황 | 응답 |
| --- | --- |
| 없거나, 삭제됐거나, 게시 전(`DRAFT`) | `404 EVENT404-0` |
| 종료됐거나 시작 전이거나 종료일이 지남 | `404 EVENT404-2` |

`403` 이 아니라 `404` 인 이유는, `403` 으로 답하면 id 를 훑어 **"이 번호에 뭔가 있다"** 를
셀 수 있기 때문입니다. 같은 이유로 버전 조회도 남의 이벤트 버전을 `404` 로 답합니다.

## 5. 자기 자원은 경로에 id 를 넣지 않습니다

```
GET  /api/users/me                     내 정보
GET  /api/users/me/participations      내 참여 목록
POST /api/users/me/events/{id}/participations
```

**대상은 경로가 아니라 토큰이 정합니다.** 남의 id 를 넣어 조회·수정할 방법이 구조적으로
없습니다.

그리고 `/api/users/**` 는 `USER` 역할만 통과합니다. 관리자 토큰의 id 는 `admins` 테이블의
id 라서, 관리자가 들어오면 **엉뚱한 사용자의 데이터를 보게 됩니다.** 그래서 역할로 막습니다.

---

## 6. 소유 관리자만 바꿉니다

이벤트 수정·종료·게시·게시 내리기·휴지통 이동·복구·영구 삭제는 **그 이벤트를 만든 관리자만**
할 수 있습니다. 다른 관리자가 요청하면 `403 COMMON403-0` 이고 **아무것도 바뀌지 않습니다.**

관리자 id 는 인증 정보에서 읽습니다. 요청 본문이나 쿼리로 받지 않습니다.

> ⚠️ 현재 **버전 조회(`GET .../versions`)·체크포인트 지정에는 이 검사가 없습니다.**
> `VersionRestoreService.restore` 에는 있습니다. 메우는 중입니다.

## 7. 삭제는 두 단계입니다

```
DELETE /{id}            휴지통으로 (soft delete, deletedAt 기록)
DELETE /{id}/permanent  영구 삭제 (되돌릴 수 없음)
```

**게시 중인 이벤트는 휴지통에 못 보냅니다** (`409 EVENT409-2`). 먼저 내리거나 종료해야 합니다.

**생성 작업이 도는 이벤트도 거부합니다** (`409 EVENT409-3`). 그러지 않으면 휴지통에 간 뒤에도
백그라운드 생성이 끝나면서 **삭제된 이벤트에 새 버전이 저장**됩니다.

> 이 검사 때문에 `EventService` 가 `generation.service.GenerationJobStore` 를 참조합니다.
> 패키지 경계를 넘는 의존이고, 팀에서 허용하기로 한 예외입니다.

영구 삭제는 `event_versions` 등 하위 데이터를 DB 의 `ON DELETE CASCADE` 로 함께 지웁니다.
**참여 기록(`event_participations`)도 같이 지워지므로** 사용자의 참여·당첨 이력이 사라집니다.
그래서 **참여 기록이 하나라도 있으면 영구 삭제를 거부합니다** (`409 EVENT409-9`).

- 검사 순서는 휴지통에 없음(`404`) → 만든 관리자가 아님(`403`) → 참여 기록 있음(`409`) 입니다.
  소유자가 아니면 참여 기록이 있는지는 확인하지도 않습니다 (`EventServiceTest` 가 고정).
- 휴지통으로 보내기와 복구는 참여 기록과 상관없이 됩니다. 지워지는 것이 아니기 때문입니다.
- 참여 기록 여부는 `EventRepository.hasParticipations` 가 `EXISTS` 쿼리 한 번으로 봅니다.
  참여 엔티티를 불러오지 않고, 참여가 많아도 첫 행에서 멈춥니다.
- 참여 기록이 있는 이벤트를 정말 없애야 한다면 현재로서는 방법이 없습니다. 휴지통에 두면
  목록에서는 사라지고 사용자의 참여 이력은 남습니다.

---

## 8. 알림은 이벤트당 한 번씩만

`startNotifiedAt` · `closingSoonNotifiedAt` · `endNotifiedAt` 을 이벤트에 기록해 같은 알림을
두 번 보내지 않습니다. 수신자는 `event.ownerAdmin` 입니다.

**게시를 내렸다 다시 올려도 재발송되지 않습니다.** 게시 내리기가 이 기록을 건드리지 않기
때문입니다 — 의도된 동작입니다.

**전체 기간이 3일 이하면 `CLOSING_SOON` 을 보내지 않습니다.** 시작하자마자 이미 마감임박이라
`STARTED` 와 겹치고, 따로 알릴 구간이 없습니다.

## 9. 멤버십 등급은 세 시점에만 다시 계산합니다

```
회원가입 · 요금제 변경 · 로그인
```

조회(`GET`)에서는 저장된 값을 그대로 씁니다. **가입기간 경과만으로 자동 승급시키는 배치를
두지 않습니다** — 실제 통신사 환경에서 등급은 별도 고객·과금 시스템이 산정한다고 보았습니다.

단점이 있습니다. 오래 로그인하지 않은 계정은 **재계산했다면 나왔을 등급보다 낮게** 남아
있을 수 있습니다. 다만 요금제가 같다면 가입기간 점수는 **오르기만** 하므로 저장값이 실제보다
**높게** 잘못될 일은 없고, 다음 로그인 때 갱신됩니다.

등급이 바뀌어도 **이미 발급된 토큰에는 즉시 반영되지 않습니다.** Access Token 이 짧아
(30분~1시간) 그 정도 지연은 허용합니다.

산정 규칙(요금 점수 + 가입기간 점수)은 `MembershipGradeCalculator` 의 주석에 있습니다.

## 10. 참여 결과의 의미 — 셋을 구별합니다

`event_participations.result_data` 는 jsonb 이고 `status` 키로 결과를 담습니다.
**빈 `{}` 와 `PENDING` 은 다릅니다.**

| 저장된 값 | 뜻 | 요약 집계 |
| --- | --- | --- |
| `{"status":"WON","prizeName":"…"}` | 당첨 또는 전원 지급 대상 | 받은 혜택에 포함 |
| `{"status":"LOST"}` | 미당첨 | 어디에도 안 들어감 |
| `{"status":"PENDING"}` | **결과 대기** (추후 추첨·예측형) | 결과 대기에 포함 |
| `{}` | **단순 참여 기록**. 결과 개념이 없는 참여 | 어디에도 안 들어감 |

**`{}` 를 결과 대기나 미당첨으로 임의 변환하지 않습니다.** 과거에 `{}` 로 저장된 기록도
자동으로 `PENDING` 이 되지 않습니다 — 그때는 결과라는 개념 자체가 없던 참여입니다.

### `WON` 은 "쿠폰이 발급됐다" 가 아닙니다

**결과가 그렇게 기록됐다**는 뜻입니다. 실제 쿠폰 발급·경품 재고 차감은 이 API 범위 밖이고,
지금 구현에 없습니다. 화면 문구를 쓸 때 "지급 완료" 로 읽히지 않게 해야 합니다.

### 조회는 다시 계산하지 않습니다

참여 목록·상세는 **저장된 값을 그대로** 보여줍니다. 조회할 때 추첨을 다시 돌리거나 결과를
계산하지 않습니다. 같은 기록을 두 번 열면 같은 답이 나와야 하기 때문입니다.

### 참여 목록은 이벤트 상태로 거르지 않습니다

이벤트가 종료됐든 휴지통에 갔든 **내 참여 기록은 그대로 보입니다.** 참여 이력은 사용자의
것이지 이벤트의 상태에 딸린 것이 아닙니다. 멤버십 등급이나 참여 기간으로도 거르지 않습니다.

> 그래서 이벤트를 **영구 삭제하면 참여 기록이 CASCADE 로 함께 사라집니다.** 사용자가 보던
> 이력이 통째로 없어지는 것이라, 참여 기록이 있으면 영구 삭제를 거부합니다
> (`409 EVENT409-9`, §7).

### 참여 방식은 `games.code` 로 판단합니다

`config` 안에 참여 방식 코드를 **다시 넣지 않습니다.** 두 군데에 있으면 어긋날 수 있고,
어느 쪽이 맞는지 정할 근거가 없습니다. 설정 API 는 기존 설정을 **조회만** 하고 생성·수정하지
않습니다.

## 11. 미리보기 HTML 은 읽기 전용으로 띄웁니다

버전 상세·미리보기가 돌려주는 HTML 은 **LLM 이 만든 것**입니다. 정화를 거치지만 화면에
넣을 때도 격리해야 합니다.

```html
<iframe sandbox srcdoc="…">   <!-- allow-same-origin 을 주지 않는다 -->
```

`allow-same-origin` 을 주면 iframe 안의 스크립트가 **부모 문서의 쿠키·DOM 에 접근**합니다.
정화를 한 번 통과한 HTML 이라도 그 권한을 줄 이유가 없습니다.

조회 API 는 **조회만** 합니다. 저장된 버전·현재 작업 내용·게시 버전을 바꾸지 않습니다.

---

## 12. 템플릿 라이브러리는 외부 HTML 을 받지 않습니다

등록은 **본인 이벤트의 저장된 버전 ID 로만** 합니다. 파일 업로드나 HTML 본문 전달이 없습니다.

```
POST /api/admin/template-library  { eventId, sourceVersionId, name, description }
```

이미 서버의 정화·검증을 통과한 HTML 만 템플릿이 됩니다. 외부 HTML 을 받으면 그 검증을
처음부터 다시 해야 하고, **템플릿은 수명이 길고 여러 이벤트에 퍼지므로** 한 번 잘못 들어가면
전부 퍼집니다.

등록할 때 **기본 제공 스크립트와 글자까지 같은 것만** 남기고 나머지 스크립트는 지웁니다.
템플릿을 쓰는 것은 **복사**라, 원래 이벤트의 버전·게시 상태는 바뀌지 않고 LLM 도 부르지
않습니다.
