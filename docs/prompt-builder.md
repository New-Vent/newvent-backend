# 프롬프트 규칙 — 왜 이 줄이 있나

`registry/PromptBuilder.java` 가 만드는 프롬프트의 **문장마다 이유**를 모았습니다.

> **문장을 고치기 전에 해당 절을 읽으세요.** 지우면 같은 사고가 다시 납니다.
> 문장을 바꾸면 이 문서도 같이 고칩니다.

절 번호(§)는 코드 주석이 가리키는 번호입니다.

---

## §0 공통 원칙 — 여러 곳에서 되풀이된 교훈

| 원칙 | 근거 |
| --- | --- |
| **예시가 말보다 세다.** 모델은 예시를 정답으로 읽는다 | 라우터 예시 유무로 content 오입력이 4건 → 0건(v11). 생성 예시가 hero · cta 뿐일 때 출력도 딱 그만큼 |
| **금지문에 이름을 쓰지 않는다.** "이럴 때는 이것" 처럼 긍정형으로 쓴다 | `v-benefits-carousel` 이 프롬프트 전체에서 "고르지 마라" 문장에만 나왔는데 모델이 거기서 이름을 배워 골랐다 |
| **서로 어긋나는 지시를 두 곳에 두면 뒤엣것이 이긴다** | §2-8 혜택 범위 사고 |
| **판단을 모델에게 맡기는 조건문 대신 단정문** | §3-7 "…일 때만" 뒤에 둔 모양 고르기를 작은 모델이 건너뜀 |
| **중요한 말은 앞과 뒤에 두 번.** 작은 모델은 가운데를 흘린다 | §3-2 |
| **목록 끝에 붙어 있기만 하면 못 고른다.** 목록 아래에서 이름을 한 번 더 짚는다 | §2-4 · §3-7 확장 짚기 (단청 사례) |
| **대괄호 `[..]` 를 쓰지 않는다** | 검증기가 자리표시자로 본다. `[hero]` 표기를 모델이 따라 써서 첫 시도 2/3 가 떨어졌다 |
| **프롬프트가 유일한 방어선인 자리가 있다** | 문체 · 배지 개수 · `benefit-*` class 이름은 검증기가 못 본다 |

## §1 공통 금지 (`지어내기_금지`) — 생성 · 수정 둘 다

```
- 날짜를 임의로 만들지 마라. 기간은 주어진 값만 쓴다.
- 주어지지 않은 혜택이나 수치를 만들어내지 마라.
- 요청문에 없는 benefit-tag 를 만들지 마라.
- 실존하는 방송 프로그램, 브랜드, 연예인 이름을 쓰지 마라.
```

- 원래 `generate()` 에만 있었는데 "4번째 혜택도 추가해줘" 는 **수정 경로**다. 한쪽만 막으면 의미가 없어서 한 곳으로 뽑았다.
- 혜택은 실제로 지급해야 하는 약속이다. "스타벅스 아메리카노 1잔" 을 지어내 게시하면 문구 오류가 아니라 사고다. 이 금지는 혜택 항목만 막는다.
- 검증기는 못 잡는다(자리표시자 검사는 대괄호만 본다). 프롬프트 · 되묻기 · 폼 값 대조(REQ-LLM-41) 세 겹 중 **첫 겹**이고, 이것만으로 0% 가 되지 않는다.

## §2 생성 프롬프트 (`generate`)

### §2-1 만들 영역 — "(선택)" 표기를 붙이지 않는다
- 붙였더니 **모델이 그걸 읽고 실제로 건너뛰었다.** 백지 생성에서 steps 가 통째로 빠졌고, required=false 라 검증도 통과해 참여 방법 없는 페이지가 저장됐다.
- required 는 검증기의 안전망이지 모델에게 줄 정보가 아니다. 드물게 정말 못 만드는 경우를 위해 required 자체는 남긴다.

### §2-2 꼭 넣을 영역 — 요청문이 부른 선택 블록
영역 목록을 **세 묶음**(만들 · 꼭 넣을 · 더할 수 있는)으로 가른다. 예전엔 둘이었고, 둘째 묶음이 머리말부터 전부 부정문이라 모델이 묶음 전체를 금지로 읽고 경품 · 쿠폰 · 일정 · 숫자를 benefits 카드로 몰아넣었다(여름 수영장).

열쇠말이 걸린 블록이 목록에 남았다는 건 서버가 이미 "요청문이 그 내용을 말한다" 고 판정했다는 뜻이다(`Block.llmBlocksFor`). 그 뒤에 "추측해서 만들지 마라" 는 앞뒤가 안 맞으므로 **만들라고 시킨다.**

| 줄 | 이유 |
| --- | --- |
| "내용이 모자라면 그 영역은 만들지 마라" | 단서가 없으면 "반드시" 가 이긴다. stats 에 숫자 하나(8,200명)뿐인데 요금제를 세어 "2종" 을 만들어 두 칸을 채웠다(여름 수영장 2차) |
| "각 내용은 한 영역에만" · "benefits 에 다시 쓰지 마라" | 경품이 benefits 와 prize 에 똑같이 두 번 나왔다 |
| "도로 가져오지 마라" + "대신 참여 자체의 이점을 쓴다" | 예전 줄("남는 게 없으면 다른 혜택을 쓴다")이 도로 가져오는 허락이 되어 coupon 섹션이 통째로 사라졌다. 금지만 하면 minItems 를 못 채워 재시도가 도니, 쓸 것을 이름으로 정해 준다 |

### §2-3 더할 수 있는 영역
- faq · compare 금지 줄은 **그 블록이 목록에 없을 때만** 넣는다. 목록에 있는데 "만들지 마라" 면 서버 판정과 정면으로 어긋난다.
- faq 는 "관련 내용" 만으로 약했다 — 요청하지 않은 VIP 이벤트에서 질문 4개를 지어냈고 답이 "별도 공지 · 고객센터 문의" 였다. 직접 요청 기준으로 좁히고 내용 없는 답을 금지한다.
- 빠진 블록 이름을 **직접 말한다**("이번 요청에서는 … 영역을 만들지 마라"). 목록에서 빼기만 하면 이름을 몰라도 비슷한 걸 만든다. 그래도 만들면 `BlockValidator.dropUntriggered` 가 지운다.

### §2-4 모양 고르기 (`addLooks`)
- **"다양하게 섞어라" 를 명시**한다. 안 그러면 예시에 나온 것만 매번 고른다.
- **"딱 맞는 이름이 없으면 가장 가까운 것"** — 없으면 모델이 이름을 지어내고, `cleanLooks` 가 지워 화면은 그대로인데 "반영했어요" 가 나간다.
- **전부 싣지 않는다.** 변형이 100개를 넘어 다 실으면 입력이 두 배다. 블록마다 표본 몇 개(`Variant.sample`) + 요청문이 부른 확장(`Variant.forPrompt`). 같은 요청문이면 같은 목록이라 재시도가 흔들리지 않고, 요청문이 다르면 페이지마다 모양이 갈린다.
- 블록 이름을 대괄호로 묶지 않는다(§0).
- **움직임**은 전부 확장이라 요청문이 부를 때만 한 줄 나간다.
- **테마를 색감보다 먼저**, 배치는 맨 뒤 — 꼴을 정하고, 색을 얹고, 자리를 정한다.
- 테마에 금지문을 쓰지 않는다(§0). BASIC 의 desc 가 "분위기가 분명하지 않으면 이것" 이라는 긍정형 출구다. 목록 밖 이름은 `BlockValidator` 가 지운다.
- 팔레트에서 `palette-base` 는 뺀다 — 생성에는 되돌릴 원래 색이 없다.
- 페이지 배치도 기본 / 확장이다. 확장 배치(벽돌 · 타임라인 · L자 · 참여 레일)는 요청문이 부를 때만 싣는다(`Layout.forPrompt`) — 다 실으면 보통 요청이 비용 상한 9,000자를 넘었다(9,129자).
- **배치 고르는 기준**을 준다. 목록만 주면 모델이 배치를 건너뛴다(안 붙여도 틀린 출력이 아니라서). Bedrock 에서 배치를 말하지 않은 요청은 전부 기본 배치로 나왔다. 조건(영역 수)은 적지 않는다 — 모자라면 서버가 기본으로 되돌린다(`PageShell.settleLayout`).

### §2-5 문구 꾸밈 (`addInline`, 생성 · 수정 공통)
- "아껴 써라" 를 붙인다. 안 붙이면 문장마다 배지를 단다. 개수는 검증기가 안 센다.
- 혜택 `<li>` 바로 안의 꼬리말은 `t-badge` 가 아니라 `benefit-tag` 다(카드 왼쪽 위 꼬리말 자리). **요청문에 한정 · 할인율 · 선착순 · 등수가 있을 때만** 쓴다. "써라" 로만 쓰면 "헬스장 등록권 추가" 에도 꼬리말이 붙는다. 생성 `volumeRules` · §1 금지와 말을 맞춘다.

### §2-6 마크업 규칙
- "class 이름은 글자 그대로" — `benefit-*` · `step-*` · `badge` 는 접두사가 달라 `cleanLooks` 의 허용 목록 검사를 지나간다. 모델이 `benefit-headline` 같은 걸 지어내면 효과도 없이 그대로 저장된다. 프롬프트가 유일한 방어선.
- 머리말(`.block-header`)은 event.css 에서 `:not(.ev-block)` 제약이 없어 백지에도 걸린다. 소제목 블록이 여섯이라 shape 여섯 곳에 베끼지 않고 한 줄로 둔다.

### §2-7 예시
- benefits 와 steps 를 넣는다. 예전 예시는 hero · cta 둘뿐이었고 출력도 딱 그만큼이었다(§0).
- 혜택 카드에 **구체적인 값을 두지 않는다**(🎁 · 혜택 이름 · 조건 설명 한 장). 예전 예시의 3GB · 55,000원 → 38,500원 · 6개월 한정을 모델이 요청에 없는데도 베꼈다 — 생성 시험 22개 페이지 중 19개가 요청에 없는 수치를 담았다(#230). hero 꼬리말도 "선착순" → "이벤트".

### §2-8 분량
- **안 시키면 하한에 딱 맞춰 멈춘다.** 백지 생성 출력이 97 · 109 · 145 토큰, 페이지 전체 315자, 혜택은 minItems 2개 정확히. 유일한 압력이 검증기 하한이었다.
- 혜택은 개수가 아니라 **설명**을 늘린다(지급 약속이라 지어내면 안 된다, §1). "요청문에 없는 혜택 항목을 더하지 마라" 를 같은 줄에 붙인다(#230).
- 혜택 범위 줄은 꼭 넣을 영역(§2-2)과 **맞춘다.** "요청문에 있는 것을 빠짐없이" 를 무조건 말했더니 147줄 앞의 "benefits 에 다시 쓰지 마라" 를 이겨서 여행권이 benefits · prize 에, 쿠폰이 benefits · coupon 에 두 번씩 나왔다(§0 뒤엣것이 이긴다).
- 이모지 · 이름은 채운다 — benefit-icon 이 비면 54px 빈 사각형이 남는다. **설명(benefit-desc) · 받는 값 · 조건 · 다른 혜택은 요청문에 있을 때만** 만든다. 예전엔 "설명까지 항상 채운다" 여서 이름만 시킨 항목에도 조건 문장이 붙었다(#230, benefit-tag 와 같은 과생성).
- 참여 방법은 모델이 만드는 영역(Source.LLM)이라 요청문에 없어도 만들게 한다. 다만 '이벤트 확인 → 참여하기 → 완료' 처럼 **추첨 · 당첨 · 발표 · 응모를 말하지 않는** 절차로 — "일반적인 온라인 응모 절차" 였을 때 증정 요청에 "응모 → 당첨자 발표" 가 붙었다(#230).
- 요청문에 혜택이 없으면 '이벤트 참여' 한 항목만. 없는 추첨 · 선착순 · 참여 자격 · 일정 · 당첨 인원 · FAQ 답을 쓰지 않는다(#230).
- step-title / step-desc 는 크기 · 색이 달라 같은 문장을 넣으면 두 번 보인다. 역할을 가른다.
- 단계 번호를 글자로 쓰지 마라 — 변형이 `li::before` 로 이미 그린다.

### §2-9 문체
같은 요청문에 "즐기세요!" 와 "즐겨봐!" 가 번갈아 나왔다. 통신사 페이지에 반말은 사고이고, 검증기는 문체를 못 본다. '특별한 · 푸짐한 · 풍성한 · 프리미엄 · 놓치지 마세요' 같은 빈 과장어도 막는다(#230).

### §2-10 금지
- **생성에만** 두 줄을 더한다: 요청문에 없는 숫자(금액 · 수량 · 기간 · 인원 · 할인율 · 횟수), 요청문에 없는 상품 · 서비스 · 브랜드 이름. §1 목록은 수정도 쓰는데, 생성은 빈 문서에서 만들어 지어낼 여지가 훨씬 크다(#230).

뺀 것들:
- **"이모지를 쓰지 마라" 를 뺐다**(벤치마크 v8.4 와 다른 점). 템플릿 5종 블록에 이모지가 58개 있고 슬롯 바로 옆(📅 기간)에도 붙어 있다. 금지하면 수정할 때 모델이 지우는데 검증기가 못 잡아서 요청하지 않은 변경이 조용히 들어간다. 적극 권장도 하지 않는다 — 측정 없이 넣을 이유가 없다. 생성 통과율 영향은 **측정 전**이다(골든 세트 전후 비교 항목).
- **data-slot 을 언급하지 않는다.** 생성은 빈 문서라 슬롯이 있을 이유가 없고, "만들지 마라" 보다 개념을 모르는 게 확실하다. 만들어도 `sanitizeGenerated()` 가 지운다.

## §3 수정 프롬프트 (`edit`)

### §3-1 매개변수 — 각자 사고 하나씩을 막는다

| 매개변수 | 없을 때 생긴 일 |
| --- | --- |
| `templateBlock` | 템플릿 블록(.ev-block)에는 변형 CSS 가 안 걸려 골라도 안 바뀐다 → 변형을 안내하지 않는다. 팔레트는 루트에 걸리므로 안내한다 |
| `allowPalette` | 영역을 골라 고칠 때 팔레트를 고르면 저장 직전 루트로 옮겨져(`PageShell.hoistPalette`) 고르지 않은 영역 색까지 바뀐다 |
| `looksRequest` | 라우터의 op 이 모델에게 안 갔다. EDIT 이든 STYLE 이든 프롬프트가 같아서 "제목을 더 화려하게" 에 이모지 · `<strong>` 만 붙고 레이아웃은 오히려 밋밋해졌다 → §3-7 |
| `addItem` | 사용자 프롬프트는 "하나 더한다", 이 프롬프트는 "항목을 새로 만들지 마라" — 어느 쪽을 버려도 실패(원본 그대로 / 수치를 지어내 ValueCheck 에 걸림) |
| `assets` | 모델은 그림을 볼 수 없지만 배치는 **이름 고르는 일**이다. 변형 · 팔레트와 같은 길(서버가 목록, 모델이 하나). 자리 · 크기 · 덮개는 CSS 가 쥔다 |
| `requestText` | 요청문이 부른 확장 변형 · 팔레트 · 테마를 싣는다. null 이면 기본만 |
| `creating` | 없는 영역을 새로 만들 때 형태(shape)를 준다 → §3-3 |

### §3-2 겉모습 요청은 앞에서 한 번 더
`looksRequest` 면 머리에 "이번 요청은 겉모습을 바꾸는 요청이다" 를 둔다(§0 앞뒤 두 번).

### §3-3 형태(shape)는 새 영역에만
- 수정에서는 shape 를 주지 않는다. 템플릿 benefits 는 `.benefit-card` div 인데 "`<ul>` 안에 `<li>`" 를 주면 구조를 갈아엎어 디자인이 망가진다.
- **없는 영역을 새로 만들 때는 준다** — 갈아엎을 구조가 없다. 안 주면 "일정 영역을 추가해줘" 에 data-slot · id 를 지어낸 div 를 내서 must(`ol li`)가 없어 `empty_schedule` · `slot_invented` 로 4회 전부 터졌다(FAQ 도 같다).
- ★ `EditService` 가 `creating = before.isBlank()` 를 `PromptBuilder.edit` 에 넘겨야 한다. `createFormBlock` 만 넘기는 오버로드는 `creating` 을 false 로 고정해서 shape 가 빠졌다 — 일정·FAQ 추가가 "반영하지 못했습니다" 로만 끝났다.

### §3-4 건드리면 안 되는 것
- 생성과 반대로 슬롯을 **지키라고** 말한다. 수정 대상에는 서버가 심은 data-slot 이 있고, 지워지면 그 자리를 영영 못 채운다(merge 가 통째로 갈아끼운다).
- data-behavior 는 이름 목록을 싣지 않는다 — 모델이 동작을 고르게 하면 안 된다. 있는 것을 두라고만 한다.
- 이모지 보존을 명시한다. 템플릿 블록에 58개, 일부는 슬롯 옆. 지우면 요청받지 않은 변경인데 검증기가 못 잡는다.

### §3-5 항목 — 폼 값 블록과 항목 추가
- 항목이 관리자가 정하는 값인 블록(`itemsAreFormValues`)에만 "항목을 새로 만들거나 지우지 마라" 를 붙인다. steps 처럼 모델이 쓰는 블록에 붙이면 다듬기도 막힌다. **`if (b == Block.BENEFITS)` 로 쓰지 말 것** — 레지스트리를 만든 의미가 없다.
- 항목 추가면 그 금지문 대신 "하나만 · 같은 태그 · 같은 class · 수치 지어내지 마라" 가 나간다. "같은 class" 가 없으면 템플릿 카드를 `<li>` 로 만들어 붙여 디자인이 깨진다.
- **통째로 지운 혜택 · 경품을 다시 만들 때**(`createFormBlock`, #241)는 항목 추가 문장 대신 표준 서식(혜택: `v-benefits-grid v-surface-tint` 의 `<ul><li>` 하나, 경품: `v-prize-list` + 머리말 + `<li>` 하나, `ev-block` 금지)을 그대로 준다.

### §3-6 이미지
올린 이미지가 있을 때만 안내한다. "이미지를 넣을 수 있다" 만 알려 주면 모델이 주소를 지어낸다.

### §3-7 모양 고르기
- 고를 게 없으면 절 전체를 뺀다. 언급만 하고 목록이 없으면 목록 밖 이름을 지어낸다.
- `looksRequest` 면 **단정문**("이번 요청이 이것이다. 반드시 하나를 골라 바꾼다"). "…일 때만" 이면 모델이 해당 여부를 스스로 판단하다 쉬운 길(문구 고치기)로 샌다.
- 특정 색을 말하면 **그 색 이름이 적힌 배경**을 고르게 한다. 안 그러면 "파란색으로" 에 어두운 배경 · 그림자를 고르고 성공으로 끝난다.
- **색 지정 배경(`v-surface-blue` …)은 요청문이 그 색을 말할 때만 수정 목록에 싣는다.** 생성에는 원래 없었고, 수정에만 상시 실렸더니 "더 화려하게" 에도 파란·초록 배경이 선택지에 있어 색을 임의로 바꿨다. `Variant.forEdit` 가 `namedColorAsked` 로 거른다.
- **영역 선택 수정(팔레트 없음)**: '문구 꾸밈' 에 `t-badge-purple` 처럼 색 이름 항목이 있어서, "보라색으로" 에 모델이 VIP 같은 단어에 보라 알약을 붙이고 "v6 로 반영했어요" 가 나갔다 — 고를 게 그것뿐이었다. 그 길을 막고, 마땅치 않으면 **아무것도 바꾸지 마라**고 한다. 그러면 `EditService` 의 조용한 실패 검사가 `cannotDo()` 로 정직하게 안내한다.
- **테마**(basic · bloom · aurora …)는 원래 수정 프롬프트에 한 번도 안 나왔다 — "더 화려하게" 의 가장 큰 지렛대가 없던 셈. 배관은 이미 있다: hero class 에 붙이면 `cleanLooks` 가 하나만 남기고 `PageShell.settle` 이 루트로 올린다. **템플릿에는 안내하지 않는다** — 루트의 `theme-sports` 같은 다른 벌을 갈아끼워 디자인이 깨진다.
- "**색만** 바꿔 달라면 분위기는 그대로" — 테마는 글꼴 · 모서리 · 장식까지 쥔다. "전체 색을 파란색으로" 한 번에 레이아웃이 바뀌어 관리자가 놀랐다. 팔레트 목록과 나란히 있어 둘 다 고르니 갈라 준다.
- **되돌리기는 palette-base 라고 직접 말한다.** "원래대로 되돌려줘" 에 brand · pastel 이 붙었다(2/6) — brand 설명의 "기본" 이 "원래대로" 와 가깝게 읽힌다. BASE 설명만 고쳐서는 부족했다. "취소해줘" 에는 spring 같은 임의 색이 붙었다(채팅에 직전 수정 취소 기능은 없지만 새 색보다 원래 색이 덜 놀랍다, #226).
- 팔레트는 **이름이 분위기**(spring · lavender …)이고 색은 설명에 있다. "보라색" 에 모델이 palette-purple 을 찾다 못 찾고 아무것도 안 골랐다(설명엔 보라가 셋). 설명을 보라고 말한다.
- 확장 짚기: "전체 색을 단청 느낌으로" 에 palette-dancheong 이 목록 20번째에 있었는데 모델은 그대로 두고 요약엔 "단청 느낌으로 변경" 이라 썼다. 목록 아래에서 이름을 한 번 더 짚는다(§0).

## §4 라우터 (`router`)

- STYLE 을 "겉모양만" 으로 쓰면 색 · 굵기로 좁게 읽는다. "더 화려하게" 가 EDIT 으로 떨어져 문구만 고쳐졌다 → 분위기 요청까지 정의에 넣는다.
- **페이지 전체 색 · 분위기 · 되돌리기는 영역을 나열하지 않고 hero 하나**, 되돌리기 · 취소는 DELETE 가 아니다. 이 줄이 없을 때 "원래 색으로 되돌려줘" 등에 14개 영역 전부에 연산을 냈고(MAX_OPS 3 초과로 통째로 버려짐), "이전으로 돌려줘" 가 DELETE faq 로 샜다(#226).
- **겉모양 말이 없는 단순 만들기 · 작성 요청은 STYLE 금지(ADD)** — 위 규칙이 넓어져 "작성해줘" 가 STYLE hero 로 가 색이 바뀌었다. "색 · 분위기 · 되돌리기 말이 없으면" 으로 좁혔더니 크기 · 굵기 요청까지 막혀서(PR #226 리뷰) 겉모양 말 전부로 묶었다. 두 줄 추가 후 71/71(전 36/66).
- **예시는 줄이면 안 된다.** v11 1차에서 요청문을 통째로 content 에 넣는 일이 4건 → 예시 후 0건.
- **없는 영역 추가(FAQ · 일정) 예시도 둔다.** ADD 예시가 혜택 항목만이면 "FAQ 영역 추가해줘" 가 `ADD benefits` 로 새어 다른 영역에 붙는다.
- "원래 색으로 되돌려줘" 예시는 바로 앞 "전체 색감" 예시의 **짝**이다. 예시만으로는 부족했고 위 규칙 줄까지 있어야 같은 문장 10개가 모두 hero 하나로 갔다.
- 페이지 전체 색감 · 이미지 배경 · 페이지 배경 · 페이지 배치는 모두 **hero 의 STYLE**. 고르는 자리가 hero 이고 서버가 루트로 올린다(`hoistPalette` · `hoistPageAsset` · `settleLayout`). 예시가 없으면 "알 수 없는 영역" / "요청을 이해하지 못했습니다" 로 떨어졌다(이미지 예시가 없을 때 올리기 · 정화 · 프롬프트를 다 깔고도 라우터만 몰라 못 갔다).
- 이미지 요청의 content 는 null — "1번" 은 페이지에 쓸 문구가 아니다. 원문은 `[관리자 요청]` 으로 수정 모델에 간다.
- "혜택을 벤토로" 처럼 영역을 말하면 그 영역의 STYLE(`v-*-bento`), 영역이 없을 때만 hero.
- **마지막 두 예시는 짝**이다 — 문장 꼴이 같고 op 만 갈린다("친절하게 다듬어줘" EDIT / "화려하게" STYLE). 짝이 없을 때 "더 화려하게" 가 앞 예시를 베껴 EDIT 으로 떨어졌다. **맨 뒤에 둔다** — 모델은 마지막 예시를 제일 무겁게 읽는다.

## §5 동작 배치기 (`behaviorPlanner`)

- 방금 만든 백지 페이지에 어떤 동작을 어디에 둘지 **JSON 으로 이름만** 고른다. HTML · data-behavior 는 쓰지 않고, 검증 · 심기는 서버다(`BehaviorPlanter.decide` · `apply`).
- 동작 목록은 `Behavior.PLANNABLE` 과 짝이다. 하나를 고치면 다른 쪽도 고친다.
