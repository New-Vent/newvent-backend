# 결정 기록 (ADR)

**되돌리기 어려운 선택**과 그 이유를 한 장씩 남깁니다.

## 여기에 쓸 것인가 — 네 문항

| 질문 | |
| --- | --- |
| 되돌리는 **비용이 큰가** | 데이터 이관·인프라 재구성·여러 계층 수정이 필요한가 |
| **대안이 실제로 있었나** | "A 도 B 도 가능했는데 A 를 골랐다" 가 성립하나 |
| 다른 코드가 **그 위에 쌓이나** | 한 번 정하면 이후 구현이 이걸 전제로 깔리나 |
| 모르면 **누가 되돌릴까** | "이거 왜 이래? 고치자" 가 나올 만한가 |

**넷 다 해당하면 여기**, 아니면 다른 곳입니다.

| 성격 | 쓸 곳 |
| --- | --- |
| 되돌리기 어려운 선택 | **`decisions/`** |
| 여러 API 에 걸친 설계 배경 (바꾸기는 쉬움) | [`../api-design.md`](../api-design.md) |
| 팀 전체에 적용되는 작성 규칙 | [`../api-conventions.md`](../api-conventions.md) |
| 서버·배포 구성과 운영 | [`../infra.md`](../infra.md) |
| 한 줄로 끝나는 설명 | 코드 주석 또는 `@Operation(description=...)` |

### 예시로 보는 경계

- `closingSoon` 을 **3일**로 한 것 → 숫자 하나라 되돌리기가 쌉니다 → `api-design.md`
- 슬롯을 **보여줄 때 채우는 것** → 바꾸면 저장된 모든 버전을 다시 써야 합니다 → ADR
- nginx 를 **호스트에 둔 것** → 운영 구성이고 `infra.md` 가 맥락을 같이 담습니다 → `infra.md`

## 쓰는 법

파일명은 `{번호}-{한글 제목}.md`. 번호는 이어서 붙입니다.

```markdown
# 0005. 제목 (무엇을 하기로 했는지)

- 상태: 적용됨 | 검토 중 | 폐기됨 (→ 0009 로 대체)
- 관련 코드: 경로들

## 문제
무엇을 정해야 했는지. **고를 수 있었던 대안**을 같이 적습니다.

## 결정
무엇으로 정했는지.

## 이유
왜 그쪽인지. **반대 선택이 왜 안 되는지**가 핵심입니다.

## 결과
좋은 점과 **치러야 하는 비용**. 비용을 안 적으면 다음 사람이 믿지 않습니다.
```

**바뀐 결정은 지우지 말고 `폐기됨` 으로 표시하고 새 번호를 가리킵니다.** 왜 바꿨는지가
결정 자체만큼 중요합니다.
