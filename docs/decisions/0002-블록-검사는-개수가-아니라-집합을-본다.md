# 0002. 블록 보존 검사는 개수가 아니라 이름표의 집합을 본다

- 상태: 적용됨
- 관련 코드: `registry/BlockValidator.checkPreserved` · `registry/Slots.keysOf`

## 문제

관리자가 채팅으로 블록을 수정하면 LLM 이 그 블록의 HTML 을 다시 써서 돌려줍니다.
그때 **지우면 안 되는 것**이 섞여 있습니다.

```
data-slot   서버가 값을 쓰는 자리. 없어지면 그 이벤트는 영영 못 채운다
id          getElementById 로 직접 찾는다 (#demoTimer · #regCount)
class       변형(v-*)과 팔레트가 걸리는 이름
```

이것들이 그대로인지 어떻게 확인할 것인가.

## 결정

**개수가 아니라 "이름의 집합" 이 그대로인지 봅니다.**

```java
diff(Slots.keysOf(before), Slots.keysOf(after), ...)   // Set<String> 비교
```

## 이유

개수를 묶으면 **정상 요청이 영원히 실패합니다.**

```
"복주머니를 2개만 보여줘"     → 카드 3개 → 2개.  개수가 줄어서 거부됨
"혜택을 하나 더 추가해줘"      → 카드 3개 → 4개.  개수가 늘어서 거부됨
```

템플릿 5종의 스크립트는 전부 **이벤트 위임**입니다. `document` 에 리스너 하나를 걸고
`closest('.cta-btn, .btn')` 으로 판정합니다. **그래서 버튼을 복제해도 그대로 동작합니다.**
개수를 고정할 기술적 이유가 없습니다.

## 결과

**좋은 점** — 카드 추가·삭제 요청이 통과합니다.

**치러야 하는 비용 — 일부만 사라진 것을 못 잡습니다.**

버튼 3개에 같은 이름표가 붙어 있을 때, LLM 이 그중 2개의 속성을 지워도 집합에는 그 이름이
**하나 남아 있어서** 검사를 통과합니다. 죽은 버튼 2개가 그대로 게시됩니다.

슬롯은 종류가 둘(`period` · `cta-link`)뿐이라 이 위험이 작습니다. 다만 **요소마다 하나씩
붙는 이름표**(예: `data-behavior`)에 같은 방식을 쓰면 위험이 커집니다 — 그때는 개수나
위치까지 봐야 합니다.

## 대신 고정하는 것

집합으로 느슨하게 보는 대신, 아래 둘은 엄격하게 봅니다.

```
id         복제하면 id 가 중복돼 getElementById 가 첫 번째만 잡는다
class      단, 이름표가 붙은 요소의 것만 (diffClasses)
```

항목 수는 `container` 의 자식 수와 `must` 선택자 개수로 **늘어난 것만** 막습니다
(`ITEM_ADDED`). 줄어드는 것은 허용합니다.
