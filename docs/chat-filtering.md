# 관리자 채팅 개인정보 포함 확인

> 적용 기준: 2026-09-30, feat/filtering. 금지 표현 검사는 사용하지 않는다.

## 1. 확정한 처리 방식

- 표현의 적절성은 관리자가 검수·직접 편집한다. 금지어 목록, 입력 차단, 금지어 출력 검사 및 재시도는 제거했다.
- 이메일·전화번호·주소 등 개인정보 후보를 서버가 감지하면 바로 LLM에 보내지 않고 포함 여부를 확인한다.
- 관리자가 명시적으로 확인하면 원문을 LLM에 전달한다. 자동 마스킹하거나 자리표시자로 바꾸지 않는다.
- 확인하지 않으면 LLM 호출과 새 버전 저장이 발생하지 않는다.
- 이번에 추가했던 일반 문장 모호성 및 서버 변경 표현의 정규식 검사는 제거했다. 기존 라우터/Gate의 되묻기·서버 소유 블록 보호·HTML 정화·값 검증은 유지한다.

## 2. 탐지 범위

| 대상 | 지원 예시 | 처리 |
| --- | --- | --- |
| 이메일 | test@example.com | 포함 확인 |
| 전화번호 | 010-1234-5678, 02-123-4567, 031-1234-5678, +82 10 1234 5678 | 포함 확인 |
| 국내 도로명 주소 | 서울 강남구 테헤란로 123 | 포함 확인 |
| 국내 지번 주소 | 서울 강남구 역삼동 123-4 | 포함 확인 |
| 주민등록번호 형태 | 생년월일 6자리 + 식별번호 7자리 | 자동 차단 대신 포함 확인 |

탐지는 패턴 기반이며 개인정보 여부를 확정하는 판정이 아니다. 주소는 도로명/동·읍·면·리와 번지 숫자가 명시된 형태를 대상으로 한다.
건물명만 적힌 주소, 외국 주소, 이름, 계좌번호, 모든 우회 표기를 포괄하지 않으며 오탐·미탐이 가능하다.
정규화는 탐지용으로만 사용한다. 확인 후 전달되는 요청은 기존 제어문자 정리 외에는 원문을 유지한다.

## 3. 프론트 화면

확인 질문 예시:

> 이메일, 전화번호 정보가 포함되어 있습니다. 해당 정보를 LLM에 전달하고 이벤트 페이지에 포함할 수 있습니다. 그대로 진행할까요?

질문에는 감지된 정보의 종류만 표시한다. 서버 응답에 개인정보 원문이나 해시를 넣지 않는다.

| 버튼 | 동작 |
| --- | --- |
| 포함하고 진행 | 원래 요청문을 그대로 재전송하고 privacyConfirmed=true, privacyConfirmationJobId=확인 작업 ID 전달 |
| 내용 수정 | 전송 전 요청문을 다시 편집. 확인 ID와 확인 값을 지우고 새 요청으로 전송 |
| 취소 | 후속 요청을 보내지 않고 확인 UI를 닫음. 기존 미리보기/버전 유지 |

자유 답변 '네'를 동의로 해석하지 않는다. 기존 미리보기는 확인이 끝날 때까지 그대로 유지한다.
개인정보 확인은 페이지 게시 승인이 아니다. 처리 성공 후에도 기존 검수·게시 절차를 따른다.

## 4. API 연결

| 용도 | 메서드 | 경로 |
| --- | --- | --- |
| 백지 생성 | POST | /api/admin/events/{eventId}/generate |
| 채팅 수정 | POST | /api/admin/events/{eventId}/edit |
| 생성·수정 상태 조회 | GET | /api/admin/events/{eventId}/generate/{jobId} |

기존 관리자 인증을 사용한다. 시작 API는 이벤트 소유자를 확인한다.

### 최초 요청

```json
{
  "requestText": "문의 이메일을 event@example.com으로 바꿔줘"
}
```

백지 생성은 templateCode=null을 사용한다. 이벤트에 템플릿이 연결돼 있으면 기존 생성 API의 템플릿 선택 규칙이 우선하므로, templateCode=null만으로 백지 경로를 강제할 수 있는 것은 아니다.

시작 응답은 HTTP 202이며 data에 jobId, phase, percent가 있다. 개인정보 확인 대기는 시작 응답부터 ASK_BACK일 수 있다.
프론트는 jobId로 상태 조회를 한 번 수행해 질문과 개인정보 확인 필드를 읽는다.

### 상태 조회 필드

| 필드 | 의미 |
| --- | --- |
| data.phase=ASK_BACK | 확인 필요 |
| data.done=true | 이번 작업의 폴링 종료. 생성 성공이라는 뜻은 아님 |
| data.message | 관리자에게 보여줄 확인 질문 |
| data.privacyConfirmationRequired=true | 개인정보 포함 확인 버튼을 표시 |
| data.privacyTypes | EMAIL, PHONE, ADDRESS, RESIDENT_NUMBER 중 감지된 종류 |
| data.versionId=null | 아직 새 버전이 없음 |

기존 inputMasked 필드는 제거했다. privacyConfirmationRequired와 privacyTypes를 사용한다.
이전 초안의 clarificationJobId는 privacyConfirmationJobId로 변경했다. 일반 대화 연결용으로 사용하지 않는다.

### 포함 확인 요청

최초 요청과 동일한 API에 보낸다. 아래 UUID는 실제 확인 작업 ID로 대체한다.

```json
{
  "requestText": "문의 이메일을 event@example.com으로 바꿔줘",
  "privacyConfirmationJobId": "00000000-0000-4000-8000-000000000001",
  "privacyConfirmed": true
}
```

- requestText는 질문을 받았던 원래 요청문이다. '네'나 질문 메시지를 보내지 않는다.
- 서버는 작업 ID·이벤트·생성/수정 경로·만료·기준 버전과 제목/요청 해시를 대조한다.
- privacyConfirmed=true만 보내거나 내용을 바꿔 보내면 확인 우회로 처리하지 않고 거절한다.
- 확인 후 새 jobId를 받으면 새 작업을 조회한다. 성공한 versionId로 미리보기를 갱신한다.
- privacyConfirmed는 생략 시 false다. 이전 확인 값을 새 요청에 재사용하지 않는다.

### 기존 일반 되묻기와의 구분

라우터/Gate에서 나온 일반 ASK_BACK은 privacyConfirmationRequired=false다.
일반 되묻기의 이전 요청·질문·답변을 서버에서 누적하지 않는다. 관리자는 내용을 보완한 단일 요청을 기존 API로 다시 보낸다.
일반 ASK_BACK의 jobId를 privacyConfirmationJobId로 보내면 거절한다.

## 5. 실패 및 수명

| 코드 | 처리 |
| --- | --- |
| FILTER409-0 | 없는 작업, 다른 이벤트/경로, ASK_BACK이 아닌 작업, 30분 만료. 새 요청 안내 |
| FILTER409-1 | 수정 기준 버전 변경. 현재 버전에서 다시 요청 |
| FILTER409-2 | 확인 작업 없이 동의하거나 요청/제목 변경, 개인정보 질문에 확인 값 없이 응답. 다시 확인 |

최초 요청과 개인정보 확인 재요청 모두 기존 단일 요청문 500자 제한을 유지한다. 별도 누적 문맥 상한은 두지 않는다. 작업은 인메모리로 관리하며 재시작 시 사라진다. 다중 인스턴스 간 공유되지 않는다.
개인정보 확인을 위해 대화 원문이나 이전 문맥을 저장하지 않고, 해시·감지 종류·처리 경로·기준 버전만 보관한다. 프론트가 원문을 재전송해야 한다.
명시적 확인 후에는 원문이 모델 입력과 생성 HTML에 포함될 수 있다.

## 6. 적용 경계

- 대상은 백지 생성·채팅 수정의 단일 요청문과 모델에 전달하는 이벤트 제목이다.
- 기존 저장 HTML에 이미 있는 개인정보, 직접 편집 API, 템플릿 선택 경로, 첨부파일 전체를 검사하는 기능은 아니다.
- 관리자 확인은 입력 사용 허용이며, 모델이 요청을 정확히 반영했는지는 별도의 결과 검증·미리보기에서 확인한다.
- 개인정보 확인값을 영구 감사 기록으로 남기는 테이블은 추가하지 않았다.
- 작업 조회·중단 API의 이벤트 소유자 검사는 기존 후속 보완 항목이다. 시작 API의 소유자 검사와 혼동하지 않는다.

## 7. 프론트 연결 체크리스트

- [ ] inputMasked 참조 제거 및 새 확인 필드 반영
- [ ] 개인정보 확인 UI에 포함하고 진행 / 내용 수정 / 취소 제공
- [ ] 확인 대상인 단일 요청문을 화면 메모리에 보관
- [ ] 포함 확인 시 원문 + 직전 질문 ID + privacyConfirmed=true 전송
- [ ] 내용 변경/새 요청/이벤트 이동 시 이전 확인 ID와 동의 값 해제
- [ ] ASK_BACK에서는 성공 안내·미리보기 교체·추가 버전 생성 처리 금지
- [ ] 실패/만료/버전 변경 시 자동 동의 재전송 금지

## 8. 검증 시나리오

- 개인정보 감지 → ASK_BACK, 라우터/생성 모델 호출 0회, 새 버전 없음
- 동일 요청에 명시적 동의 → 원문으로 생성·수정 진행
- 다른 요청/제목/이벤트/경로/버전/만료 ID → 확인 재사용 거절
- 전화번호·이메일·도로명·지번 탐지, 일반 혜택 수치 유지
- 내용에서 개인정보 제거 후 새 요청 → 확인 없이 정상 처리
- 금지 표현 및 일반 문체 요청 → 새 입력 정책에서 차단하지 않음

- 최초/확인 요청의 500자 허용·501자 거절
- 일반 ASK_BACK ID를 개인정보 확인 ID로 사용할 수 없음

실모델·브라우저·DB를 포함한 통합 검증은 별도다.
